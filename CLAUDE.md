# Spin A Doc — règles de travail et état du projet

Version publique : aucun chemin local, nom ni adresse personnelle. Les informations propres à un poste (chemins, dépôt privé, dossiers de
documents réels) vont dans `CLAUDE.local.md`, ignoré par git (`.gitignore`). Avant toute publication : `node scripts/scan-private.js`
(motifs privés dans un fichier HORS du dépôt, voir l'en-tête du script ; résultat attendu : aucune donnée personnelle).

Éditeur/visionneuse PDF Windows (Electron, JS sans framework). Produit : « Spin A Doc ».
Dépôt : GitHub (branche main). Règle : un push à la fin de chaque sous-étape, après le commit (jamais de --force, jamais d'.exe/.pdf/secret dans git ; installeurs hors git).
Contraintes permanentes : licences permissives uniquement (jamais GPL/AGPL/LGPL), 100 % hors-ligne (CSP stricte), interface en français,
annotations « figées » à l'enregistrement (aperçu et écriture partagent la même géométrie), outils persistants, panneaux flottants.
Protocole : un lot / une sous-étape à la fois, rapport court au format habituel (fait / tests / non testé / choix / limites / checklist manuelle /
commits), puis ATTENDRE le « go » de l'utilisateur. Ne jamais prétendre avoir testé ce qui ne l'a pas été.

## Règles de travail (valables pour tout le reste du projet)
**Tests ciblés, par niveaux**
- En développement : lancer UNIQUEMENT le test du module touché (ex. `node test/test-measure.js`), un test en échec se relance seul. Tests
  d'interface (CDP) : seulement le fichier concerné, après un morceau cohérent.
- Suite complète (`npm test` + `npm run test:ui` + `npm run licences`) : UNE fois par sous-étape, avant le build. Verte = pas de relance.
- Build (`npm run dist`) : une seule fois en fin de sous-étape. `test:packaged` : une fois après le build, seulement accueil + smoke test
  (démarrage, ouverture d'un PDF, rendu) ; version installée seulement si build/installeur/userData/vendor/preload ont changé.
- Ne jamais relancer une vérification verte si le code concerné n'a pas changé (`git diff`). Tenir le tableau module → test → commit ci-dessous.
- Pas de régression : on ne supprime pas de tests. Un bug corrigé reçoit un test court et précis. Une seule vérification visuelle par fonctionnalité.
- Test lent : dire quelle partie est lente et proposer une accélération avant de relancer en boucle.
**Tests en arrière-plan**
- Les tests d'interface ne doivent jamais gêner l'utilisateur : `SPIN_TEST_HEADLESS=1` (défaut dans `test/lib/app.js`) → fenêtres hors écran
  (`show:false`, `offscreen:true`, `backgroundThrottling:false`), sans focus. Captures = `capturePage`/CDP, jamais le bureau. Aucune souris/clavier
  système, aucune fenêtre de l'utilisateur touchée. Lancer en arrière-plan (`run_in_background` ou `node scripts/bg.js <test>` → `test-logs/`), lire le journal.
- Afficher une vraie fenêtre (barre de titre réelle…) : prévenir l'utilisateur avant, et regrouper en un seul passage (`SPIN_TEST_HEADLESS=0`).
- Dossiers de documents réels de l'utilisateur : lecture seule uniquement (chemins dans CLAUDE.local.md).
**Suivi des tâches en temps réel** (liste de tâches de l'application)
- Avant de commencer une tâche : « en cours » (une seule à la fois). Dès qu'elle est finie ET vérifiée par son test ciblé : « terminée » immédiatement, avant la suivante ; pas de mises à jour groupées.
- Travail imprévu (bug, test manquant) : ajouter la tâche au moment où on le découvre. Tâche échouée ou bloquée : la laisser « en cours » et dire pourquoi, ne pas la cocher.
- À la réception d'une consigne en cours de route : remettre la liste à l'état réel (fait = coché, en cours = marqué).
**Contexte petit**
- Pas de relecture de gros fichiers : grep puis lecture ciblée ; sorties de test = échecs + résumé de 2 lignes (rediriger vers un journal).
- Petits modules (un fichier par fonctionnalité). Fichier > ~1000 lignes (annotate.js 1250, app.js 530…) : proposer un découpage avant d'y ajouter du code.
- Fin de sous-étape : mettre à jour CE fichier et dire « Contexte à l'état X % : tu peux faire /clear (ou /compact) en toute sécurité ».
- Rapports courts : sans répéter ce qui n'a pas changé ; « Ce que je n'ai PAS pu tester » et la checklist manuelle restent complètes.
